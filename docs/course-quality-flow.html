코스 품질 개선 작업 흐름

스펙(docs/SPEC-course-quality.md)과 dev 브랜치 코드 조사 결과를 바탕으로 나눈 단위 작업 6개. 화살표는 "앞 작업이 끝나야 시작할 수 있음"입니다.

기반·측정코드 변경지시문 변경검증
전제: 모든 작업은 코스 생성 코드가 있는 dev 브랜치 기준입니다(현재 워크트리에는 없음, 기준 브랜치 확정 필요). 코스 규칙 위반 0건 합격선은 모든 작업에서 유지하고, 확인은 dev 문항만 씁니다.

1단계 · 기준선

T1

품질 지표 만들기 + 현재 기준선 측정

선행 없음
목표
고치기 전 숫자를 먼저 잡는다. 동선 총거리, 하루 시간 배분, 식당 메뉴 중복 수, 요청 반영(무장애·반려동물·동행)을 코드로 잰다.
작업 방식
순수 함수로 지표 계산을 추가하고 eval/score.py 결과표에 열을 더한다. 재배열 전후 거리는 reorder_day 입출력으로 비교한다. 기준값은 config.py에 둔다.
검증 방식
지표 함수 단위 테스트(pytest) + dev 문항으로 현재 코드의 기준선 값을 결과표에 기록.

2단계 · 코드 변경 (서로 독립, 병렬 가능)

T2

메뉴 중복 판정 + 검증 규칙

선행: T1
목표
한 코스에서 대표메뉴 키워드가 같은 식당이 겹치면 코드가 위반으로 잡고 바꾼다.
작업 방식
  • menu_main에서 키워드 추출 함수 작성
  • validate.py에 menu_duplicate 규칙 추가, repair_slots가 바꾸도록 REPAIR_RULES에 연결
  • 기존 theme_repeat와 겹치지 않게 정리
검증 방식
중복 있는/없는 코스 단위 테스트, repair 후 메뉴 중복 0건, 규칙 위반 0건 유지.
T3

요청 반영: 후보에 조건 정보 노출

선행: T1
목표
코스를 고르는 단계에서 무장애·반려동물·동행 조건이 실제로 반영되게 한다.
작업 방식
  • 후보 줄에 무장애 요약과 메뉴를 추가(원문 값만, 새로 만들지 않음)
  • 조건 질문일 때 검색 후보 순위에 조건 해당 장소 가중
  • "필수 조건으로 거르기"는 범위 밖이므로 하지 않음
검증 방식
후보 줄 형식 단위 테스트, dev의 해당 문항(c07 등)에서 요청 반영 지표 변화 확인.
T4

하루 시간 배분을 코드가 확정

선행: T1
목표
이용시간과 칸 구성을 기준으로 하루 분량·시간 배분이 어색한 코스를 코드가 가려내거나 조정한다.
작업 방식
이용시간 문장(hours_text)에서 코드로 읽히는 것만 파싱해 검증 규칙으로 추가. 읽을 수 없으면 "확인 필요"로 둔다(휴무일과 같은 방식). 기준값은 config.py.
검증 방식
파싱 단위 테스트, 시간 배분 지표 전후 비교. 합격 기준값은 T1 기준선을 보고 정해 사용자에게 확인.

3단계 · 지시문 보강

T5

지시문에 동선·메뉴 다양성·요청 반영 규칙 보강

선행: T2 · T3 · T4
목표
코드가 새로 판정하는 규칙을 LLM이 처음부터 지키게 해 재작성·교체 횟수를 줄인다.
작업 방식
DRAFT_SYSTEM에 규칙을 추가한다. Claude와 OpenAI가 같은 지시문을 받으며 한쪽 전용 문구는 만들지 않는다. 평가 문장은 퓨샷 예시에 넣지 않는다.
검증 방식
지시문 변경 전후를 dev 문항으로 같은 조건에서 비교(재작성 횟수, 지표 변화). 코드 규칙이 먼저 들어간 뒤라 효과를 분리해서 볼 수 있다.

4단계 · 최종 검증

T6

dev 평가 재측정과 회귀 확인

선행: T5
목표
스펙의 완료 기준(코드 지표 + 테스트 + dev 문항)을 충족하는지 확인한다.
작업 방식
python -m eval.run을 dev 문항으로 실행하고 T1 기준선과 같은 표에 나란히 놓는다. 실패 문항은 원인을 실행 기록에서 찾는다.
검증 방식
  • 코스 규칙 위반 0건 유지
  • 동선 총거리·메뉴 중복·요청 반영 지표가 기준선보다 나아짐
  • 전체 pytest 통과
  • holdout은 실행하지 않음

※ T2·T3·T4는 서로 다른 파일 위주라 병렬 가능하지만, 같은 validate.py와 course.py를 만지는 부분은 한 번에 하나씩 합칩니다.
